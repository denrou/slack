# Architecture

How `slack` is put together, for a first read of the code. README.md says what the tool does; CLAUDE.md says how it is worked on.

## Shape

One crate, one binary, blocking I/O throughout: a run is a handful of HTTP calls (`ureq`), the login holds one WebSocket (`tungstenite`) and the screen another, on a thread of its own, and the few lookups that run side by side go through `std::thread::scope` (`par.rs`, eight threads at most). No async runtime, deliberately: switching later would cost `api.rs` and `auth/cdp.rs`, not the pure modules.

Each module knows one thing, and the dependencies point down this list:

1. **Entry points.** `main.rs` parses the command line (clap) and dispatches. `commands.rs` has one function per command and prints the output (`send.rs` and `read.rs` print their own outcome). `tui/` is `slack` with no command.
2. **One module per thing asked of Slack.** `counts`, `prefs`, `history`, `threads`, `replies`, `directory`, `target`, `search`, `send`, `react`, `read`. Each turns one or two API methods into a typed value and knows nothing about printing.
3. **The shared model.** `view.rs` builds a `View` from the counts; the text rendering, `--json` and the TUI all read that same value. `mrkdwn.rs` and `style.rs` turn Slack markup into terminal text, `emoji.rs` an emoji name into its character.
4. **Files on disk.** `store.rs` (credentials), `names.rs` (the id-to-name cache), `lastview.rs` (what the last output showed), `files.rs` (the copies of posted files the screen opens), all through `paths.rs`.
5. **Transport.** `api.rs`: `Client::call(method, params)`, `Client::socket` for the screen's socket and `Client::download` for a posted file, and nothing else. No module above it sees a header or a token.
6. **Login.** `auth/`, used by `login` and `logout` only: `chrome.rs` runs the browser, `cdp.rs` talks to it, `capture.rs` picks the credentials out of what it sees.

## A run, step by step

**`slack unreads`, the view.** `Workspaces::load` picks the default workspace and builds its `Client`. `counts::fetch` calls `client.counts` and `users.prefs.get` in two threads and flags the muted conversations. `view::build` sorts the unread conversations into direct messages, mentions and channels, reads the unread part of each (`history::fetch`, `conversations.history` from the read cursor, through `par::map`) and the followed threads (`threads::fetch`), then fills the names it needs from the cache (`users.info` and `conversations.info` on a miss). `lastview::remember` records what was shown; a failure there is a warning, the view still prints. Then `--json` serialises the `View`, or `view::render` prints it.

**`slack --count`.** `counts::fetch` and `Counts::unread_count` (with `--json`, `Counts::me_count` beside it and `notify::covered`, whether a screen's heartbeat is fresh), nothing else: no names, no cache file, two calls side by side. Any failure exits non-zero with a message on stderr, so a status bar can tell "nothing" from "broken".

**`slack send`.** `target::resolve` turns the argument into a channel id and maybe a thread: a number from the last output (`lastview::thread_ref`), a permalink, a bare id, `#channel` or `@person` through the names cache with a `conversations.list` or `users.list` walk on a miss (`@person` opens the DM with `conversations.open`). Then `mention::link` on the text, `chat.postMessage`, and `chat.getPermalink` best effort for the line printed.

**`slack react`.** A permalink names the message itself (not its thread, as for `send`); anything else goes through `target::resolve`, with `--ts` for the message, or a thread number's root. `emoji::name_of` turns `:+1:` or 👍 into Slack's name, then `reactions.add` or `reactions.remove` (`react::set`).

**`slack read`.** `lastview::recall` gives the conversations of the last output with the newest message each had. Without arguments the ones the view listed are taken; with arguments each is resolved and must be in the record. A fresh `client.counts` gives the current cursors: one already past the recorded message is left alone (a cursor only moves forward), the others get `conversations.mark` at the recorded message. The marked ones are dropped from the record.

**`slack show`, `slack thread`.** `show` resolves the target, reads the newest page (`history::fetch` without a cursor) and `conversations.info` for the read cursor side by side, records the conversation and the threads it numbered (`lastview::remember_conversation`) and prints with a `── new ──` line at the cursor. `thread` takes a number or a permalink, reads `conversations.replies` (`replies::fetch`) and prints the root, then the replies.

**`slack search`.** `search::fetch` calls `search.messages` (newest first, one page of `-n`, 100 at most) and takes each match's thread from its permalink, since a match carries no `thread_ts`; `search::name` fills the names the matches need. Each prints under its conversation through `view::render_messages`, its permalink under it; how many matched beyond the page goes to stderr.

**`slack channels`, `slack people`.** `directory.rs`. The conversations you are in are the `client.counts` ids, named from the cache (one `users.conversations` walk fills it). The people are those you have a DM with, or the whole directory (`users.list`) when a filter is given.

**`slack`, the interactive view.** `main.rs` opens it only with a terminal on stdin and stdout; a pipe gets `slack unreads`. The same `View`, built with `Reach::Recent` (the recent history of each conversation rather than its unread part, `view::recent`: one page of 200 at most, trimmed to today's messages and the unread ones but never fewer than the last 50, and each unread thread whole through `replies::fetch`, with the read cursor so the screen tells the new part apart), turned into `Item`s (`Item::from_view`), followed by the conversations of `Counts::recent` that are not unread (`tui::recent`, `Item::recent`), without their history. The loop in `tui/mod.rs` draws, polls a key, hands it to `State::key`, which is pure and returns an `Action`, and performs that action with blocking calls while a status line shows. The actions use the same modules as the commands (`history`, `replies`, `directory`, `chat.postMessage`, `conversations.mark`; `subscriptions.thread.mark` for a thread). A dead session ends the program; any other error is a status line and the list stays as it was.

**`slack login`.** `chrome::launch` starts the browser on the CLI's own profile with remote debugging on a free port; `cdp::Session` connects to the page; `capture::capture` loads Slack, waits for the sign-in, and collects the `d` cookie, the `xoxc` token from the web client's own requests and the workspace list from `localConfig_v2`; `auth.test` checks each workspace and `Workspaces::upsert` saves them. `logout` deletes the store, the files the screen downloaded (`files::clear`), and the profile when the sentinel says the CLI created it.

## Module by module

- `main.rs`: clap definitions and dispatch. No subcommand is the interactive view, or the text one without a terminal; `--count` is the status-bar path.
- `commands.rs`: one function per command, where the output is printed. `show` reads a conversation's recent history (`conversations.history` without a cursor, `conversations.info` for the read cursor that places the `── new ──` line) and records it in `lastview` so `slack read <name>` and the thread numbers work from that output.
- `api.rs`: the one transport. A form POST to `<workspace url>/api/<method>` with `token=<xoxc>` in the body and `Cookie: d=<xoxd>`, the way the web client does it. Parses the `ok` envelope, maps `invalid_auth` and friends to `Error::Auth` ("run `slack login`"), retries HTTP 429 twice honouring `Retry-After` (capped at 30 s). Commands never see headers or tokens.
- `store.rs`: `~/.config/slack/workspaces.json`, workspaces keyed by team id with their credentials, written atomically with mode `0600`. `Workspace` has no `Debug` so a token can never land in a log.
- `paths.rs`: XDG lookup (`~/.config/slack`, not `~/Library/Application Support`) and owner-only file writes.
- `config.rs`: `~/.config/slack/config.toml`, the settings written by hand: `fix_command` alone so far. No file is every setting off; an unknown key is an error, so a typo does not silently turn a setting off. The screen loads it once, on opening, and a config that does not read is a warning, never a screen that does not open, and Ctrl-G then shows why rather than asking for a `fix_command` already there.
- `fix.rs`: the reply box's correction. `prompt` is the instructions (accents, typos, grammar, never the wording; markup, mentions, code and URLs untouched) with the draft between `<message>` tags, `cleaned` drops the tags a model echoes, `run` pipes the prompt through `sh -c <fix_command>` from the temporary directory (an agent CLI reads the project of the directory it starts in), the pipes on their own threads, in a process group of its own that is killed whole after 30 seconds; a failure is the last line of its stderr.
- `auth/chrome.rs`: find Chrome, launch it with `--remote-debugging-port=0` on our own profile, read `DevToolsActivePort`, find the page target, shut down (SIGTERM, SIGKILL, then `pkill -f user-data-dir=<profile>` for the helpers Chrome leaves behind). The profile is owned through a sentinel file; `logout` deletes only an owned profile.
- `auth/cdp.rs`: a hand-rolled CDP session over one WebSocket: numbered commands, buffered events, read timeouts on the socket so a poll never blocks.
- `auth/capture.rs`: the capture policy and its pure extractors (`xoxc` from a request body in the three encodings Slack uses, the `d` cookie, the workspace list in `localConfig_v2`, the origin gate). Ported from slackcli's `browser-auth.ts`; the tests pin the parsing rules.
- `counts.rs`: `client.counts` into `Conversation`s and the `Threads` block. Every conversation with something new counts, plus one for threads; a muted one counts for a channel mention only, like the app's badges. `fetch` also reads the notification preferences (`prefs.rs`, `users.prefs.get`, the `muted` flag inside the `all_notifications_prefs` JSON string) in a second thread, the emoji used most (`emoji_use`, a JSON string of name to count, ranked into `Counts::frequent_emoji` for the screen's `R`) and the conversations visited last (`recents`, a JSON string whose `navigation` list is the app's own recent list from every client, into `Counts::recent` for the screen's recent sections). When they cannot be read, a warning says so, nothing reads as muted and `Counts::prefs_missing` is set. No local lists: Slack's own mute list is the source, so the way to keep a channel out of the view is to mute it in Slack.
- `view.rs`: the model (`View`: direct messages, mentions, channels, threads) built from the counts, then rendered as text or `--json`. The model is kept apart from the rendering so the TUI sits on the same data. `Reach` says how much of each conversation is read: the unread part for the text view, the recent history with the read cursor for the screen, which also reads each unread thread whole (`Thread::history`; one that fails keeps its new replies alone, with a warning). `shown()` is what `slack read` may mark.
- `history.rs`: the unread part of a conversation (`conversations.history` from `last_read`, newest page, oldest first in the output, joins and leaves dropped). `around` reads the messages on both sides of one, for a search hit: `latest` with `inclusive` for the page up to it, `oldest` alone for the page after it, which Slack answers with the messages right after it rather than the newest. A `Message` carries its `reactions` from the same answer (name, count, the users Slack lists), and `Message::react` updates them after a reaction from the screen.
- `threads.rs`: `subscriptions.thread.getView`, paginated on `current_ts`, unread threads first; a read thread ends the walk, a shape change degrades to the summary line with a warning.
- `names.rs`: the id-to-name cache (`~/.cache/slack/names.json`), filled per id on a miss through `users.info` and `conversations.info`, a few lookups at a time, or in one walk (`users.conversations` for everything you are in, `users.list` for the directory) when the directory needs it whole.
- `directory.rs`: every conversation you are in (`client.counts` ids, named from the cache) and everyone in the workspace, with the word filter: behind `slack channels`, `slack people` and the TUI picker.
- `emoji.rs`: Slack's emoji names to characters through the `emojis` crate (gemoji's shortcodes), falling back to the Unicode name (`thinking_face`), Slack's hyphenated gendered names (`man-shrugging`) and a short alias list; skin tones follow `::skin-tone-N`. A workspace's custom emoji have no character and stay `:name:`. `matching` and `begins` are the `R` prompt's filter. `same` holds two names for one emoji (`thumbsup` and `+1`) by their character, which is how the prompt, the toggle and `Message::react` match a reaction; `other_names` gives the spellings to try when Slack refuses gemoji's (its alias, the Unicode name, the other shortcodes).
- `mrkdwn.rs`: Slack markup to terminal text. `pieces` reads a message into `Piece`s, text with its `Look` (bold, italic, strike, code; a name, a mention or a link) and markers with what was typed and what a styled view shows instead (a `▎` bar for a quote, and after each line break of a `>>>` quote, which runs to the end of the message; a line break that sets a code block apart; else nothing). Mentions, channel links and URLs (a label that only repeats the URL dropped) are expanded first and stay whole, so markup goes around them and never into them; entities are decoded; code shields its contents; bold, italic and strike nest and need a word boundary. `render` paints the pieces for the text view, or with colours off writes them back as typed so a pipe loses nothing; `strip` drops the markers for a title, an excerpt or a notification, all but a `>>>` quote's line breaks, so a code block or a quote does not cut a title short; `draft` reads the reply box's text without expanding anything. `links` lists the URLs of a message. Pure, with the parsing rules pinned by tests.
- `lastview.rs`: `~/.cache/slack/last-view.json`, the conversations the last view showed with the newest message each had, and the threads it numbered (`View::thread_refs`, reading order), which `slack thread 2` and `slack send 2` resolve. `slack show` adds its conversation and replaces the numbering: a number refers to the last output that printed one.
- `search.rs`: `search.messages` into `Hit`s (the channel, the message, its permalink), and `Hit::anchor`, the channel message to read a hit around: the thread's root for a reply.
- `replies.rs`: `conversations.replies`, root first then every reply, up to five pages; behind `slack thread`, the TUI's thread pane and its thread items.
- `target.rs`: what a conversation argument means (`#channel`, `@person`, an id, a permalink, a thread number); the name walks (`conversations.list`, `users.list`) live in `names.rs` and fill the cache.
- `send.rs`, `react.rs` and `read.rs`: the commands that write to Slack (`chat.postMessage`, `reactions.add` and `reactions.remove`, `conversations.mark`); `react::set` takes `already_reacted` and `no_reaction` as done, since the message ends up as asked, tries `emoji::other_names` on `invalid_name` and returns the name Slack took; the screen writes the same way from `tui/mod.rs`, and `target::open_dm` opens a direct message (`conversations.open`) for an `@person` target. `read` only ever marks what `lastview` recorded, and never moves a cursor back (`read::already_read`, shared with the screen's `e`).
- `rtm.rs`: Slack's real-time socket, for the screen. `Client::socket` calls `rtm.connect` and opens the `wss://` URL it names with the cookie; a detached thread reads it with a 5-second read timeout, sends a JSON `ping` every 30 seconds, takes 60 seconds without a frame or a `goodbye` as a dead connection, and reconnects with a backoff from 1 to 60 seconds. A refused session stops it: the poll reports it. Three failures to open in a row send `Signal::Off` with the reason, which the screen shows once in the status line; the tries go on. `Event::parse` keeps the messages (a new one with its text, for a notification, edits and deletions told apart, a reply also sent to the channel taken as a reply, an edit that leaves the text alone, such as a link's preview, dropped), the moved read cursors and preferences, the reactions and `user_typing`; the rest is dropped. The endpoint answers as `LEGACY_BOT`, which is why the poll stays beside it.
- `notify.rs`: the screen's notifications. `aimed` is the `@ME` count's rule for one message heard on the socket (not yours, not an edit; a DM or group DM not muted, or a mention of you, `@here` and `@channel` outside a muted channel; a user group's mention is left out, its members unknown), `Note` its title and body, `Note::sequence` the `OSC 777` escape with every control character dropped and `;` made fullwidth, since WezTerm splits the body on it. `supported` holds the terminals that post it (WezTerm, Ghostty), from `TERM_PROGRAM`. The heartbeat is `~/.cache/slack/notifying`, written by `beat`, removed by `stop`, fresh for 90 seconds (`covered`), which is what `--count --json` reports as `notifying`.
- `mention.rs`: the `@handle` and `#channel` words of a message become `<@U…>` and `<#C…>` when the name cache knows them, from the cache alone (never a call; `@here` and `@channel` stay text), for `slack send` and the screen's reply box.
- `tui/`: `slack` with no command, ratatui 0.29 over crossterm. `model.rs` is the state and its pure key transitions (`State::key` returns an `Action`, tested); `ui.rs` draws; `mod.rs` runs the loop and performs the actions with blocking calls, a status line showing meanwhile. Two detached threads, each with a clone of the `Client`, keep it current. `rtm::listen` holds Slack's socket; each pass of the loop hands what it heard to `State::hear`, which applies a reaction, a reply's count and who is typing on the screen without a call and returns a `Wake`: `Check` for a message or a moved cursor, `Reload` for a reply in a listed or open thread or an edit or deletion of a message on the screen that a reload reads again (not an opened or recent conversation's), which the counts would not show, and a reconnection asks for a reload too. The strongest of a pass nudges `poll`, which fetches `client.counts` a second after a nudge, to gather a burst, and never within 5 seconds of its last fetch; on its own it fetches every 15 seconds while the socket is down and every 2 minutes while it is up. Between keys, and only in `Mode::Browse` or `Mode::Help`, the loop compares the latest result to the counts the list was loaded from (`Pulse`: per unread conversation its `latest`, `last_read` and mentions, plus the threads block) and reloads from those counts when they differ or a nudge asked for a reload. A poll begun before the last mark or reply finished is dropped: it still shows as unread what was just read. So is one without the preferences (`prefs_missing`), which would show every muted conversation until the next. A reload a nudge asked for is owed (`App::owed`) until one is done, so a failed poll does not lose it. Ctrl-R goes through the same `reload`. `State::replace_items` keeps the selection, the focus, the highlighted message and the open thread across a reload, holding positions by message `ts`; the open thread is fetched again with it. Under the unread sections and `Opened`, `Recent channels` and `Recent people` hold the conversations visited last in Slack, `RECENT_ROWS` of each, none listed above (`State::replace_items` drops them and groups the rest by section, in the order visited). Their history is read once the cursor rests on one for `PREVIEW_AFTER` (`State::to_preview`, timed by the loop, which waits for keys no longer than that), or at once on Enter (`Action::Preview`), and `State::preview` fills it in place; the pane says "Loading…" meanwhile, never the status line, and says it could not load when the call failed (`State::preview_failed`, cleared by a reload or by moving away). A refresh keeps a history read (`Item::keep_history`) and marks it to be read again when the counts' `latest` moved, showing the old one meanwhile. The recent sections are rebuilt without a reload when only they moved (`Visited`, beside `Pulse`). `e` on a recent conversation marks it read and keeps it listed, and a reply to it, like one to an opened conversation, reads it again in place. Tab and Shift-Tab jump to the first item of the next or previous section. Two levels of focus: the list, and the messages pane (`l` or Enter), where either again opens the highlighted message's thread in the pane (`ThreadPane`, `h` closes it). Three rules hold across the modes: `q` and Ctrl-C quit from anywhere, Esc and `h` only ever step back, moving is vim's. `r` replies where the focus is (the conversation, the highlighted message's thread, the open thread) and `s` to the conversation from anywhere in it. `o` opens the picker (`Mode::Pick`, every conversation and person from `directory.rs`; it opens in its filter, where Enter opens the highlighted match and, with nothing typed or nothing matching, hands the keys to the list where `j`/`k` move and `/` goes back to the filter; muted conversations stay out until `m`, Tab marks people as you type and clears the filter for the next name, Space marks them in the list, and Enter opens them as one group message through `conversations.open`, the person typed last joining them), and `/` opens `Mode::Search` in the list's place, the highlighted hit whole in the pane: Enter in its query line returns `Action::Search` and `State::found` fills the hits in the same mode, or goes to the hits when the query is the one they are for; Enter on a hit returns `Action::ShowHit`, and `mod.rs` reads `history::around` its anchor into an `Opened` item (`Item::around`), puts the cursor on it (`State::highlight`) and, for a reply, opens the thread pane on the reply. Closing the search, or opening a hit, keeps it in `State::last_search` for the next `/`. `c` is the same picker followed by the reply box; the chosen one lands in the `Opened` section with its recent history (`view::recent`, as the unread ones) and stays through refreshes, marks and replies (it is reloaded after a reply) until `e` closes it. `x` selects conversations for `e` in `State::checked`, keyed by channel, thread and whether it is the opened copy (one conversation can be listed both unread and opened), with the `latest` each had then; `e` returns one `Mark` per selected conversation (else one for the selected item), and `mod.rs` marks each up to that `ts`, so a message that came in after the selection stays unread. An opened one is closed without a Slack call, since closing is not reading. A marked conversation leaves the list unless something newer came in, and each leaves the selection as it is done, so after a failure the selection holds what is left. A reload drops from the selection what is no longer listed, and Esc at the list clears it. The reply box (`Mode::Compose`, a `Draft`) completes `@` and `#` words from `State::candidates`, the people and channels built from the same directory load as the picker (`Action::LoadCandidates` the first time such a word is typed, unless the picker loaded it already); Tab or Enter take the highlighted entry, and `mention::link` turns the handles into mentions when the message is sent. Every conversation item holds a history, and so does a thread item, read whole: its read part ends just before the first reply the thread view calls unread, and `e` marks up to the newest reply shown. A thread past the page cap of `replies::fetch` misses its newest replies, so it keeps the thread view's new replies alone. A thread taller than the pane, a thread item or the thread pane, keeps the pane's top row for its root, decided before the scroll so the height holds from one frame to the next (`Viewport::height` counts the rows under it); once the whole root is above, the row holds its first line as drawn, time and notes included. A message is drawn from `mrkdwn::pieces`, its markers hidden, and the reply box from `mrkdwn::draft`, its markers kept but dimmed so Backspace takes what is seen (`ui::styled_lines`). The pane dims the read part, lands the cursor on the first new message (`Item::landing`) and, in list focus, starts at the `── new ──` line (`ui::draw` reports that anchor, the pane's height, the rows of its text and the messages in view back into `State::viewport`, which is what `gg`/`G`, Ctrl-D/U and Ctrl-F/B need: from the list they scroll the pane by rows, in the pane they move the highlighted message by messages). Reactions are drawn on a line under their message, yours in blue. Someone typing (`State::typing`, by channel and thread, yours never) puts a `✎` after the item in the list and their name on the pane's bottom border, where it moves nothing in the pane; a notice not repeated within 6 seconds is dropped (`forget_typing`, each pass of the loop), and so is the sender's once the message arrives. `R` opens `Mode::React` over the highlighted message: `State::emoji_choices` offers the reactions on it, then `frequent_emoji`, then the standard names the typed part `begins`, eight at most, and the typed name itself when nothing matches (a custom emoji not used yet); Enter returns `Action::React`, which adds, or removes when the emoji is already yours, and `State::apply_reaction` updates the message in the list and the thread pane without a reload. Someone else's comes through the socket and is applied the same way. `u` and `y` open or copy a link of the highlighted message (`mrkdwn::links`, then the message's `history::File`s, each a `Target`; `Mode::Links` asks which when there are several): the browser through `open` or `xdg-open`, the clipboard through `pbcopy`, `wl-copy` or `xclip`. A file copies its page in Slack (`permalink`). A file opened is `Action::ShowFile` when `File::is_drawn` (a PNG, JPEG or WebP with a preview), else `Action::OpenFile`. `ShowFile` fetches the largest preview up to 1024 pixels (`files::fetch`, `Copy::Thumb`), decodes it with the `image` crate and puts it in `App::image` as a `ratatui_image` `StatefulProtocol`, then `Mode::Image` draws it over the messages pane, re-encoded when the pane's size changes; `u` there is `OpenFile`, `y` copies its page, any other key closes it, and the screen is cleared once it closes, since some terminals keep a picture over text drawn into its cells. `OpenFile` fetches the file itself (`Copy::Original`) and hands the copy to `open` or `xdg-open`, the GIFs among them, which would show their first frame only here; a file Slack only links to, outside slack.com, goes to the browser as a link, without the cookie. How the terminal draws a picture (kitty, iTerm2, sixel, else half blocks) and its cell size are asked once at startup (`Picker::from_query_stdio`), before the first key is read, since the answer comes on the same input. Marking a thread read uses `subscriptions.thread.mark` (channel, thread_ts, ts, read=1), an undocumented call written from memory and not yet verified live: if Slack refuses it, the status line shows the error and that is the first thing to fix. A paste arrives as one event (bracketed paste) and goes to the reply box or the picker's filter, never to the keys. Ctrl-J breaks the line in the reply box; Ctrl-Enter and Shift-Enter do too, which takes the kitty keyboard protocol's disambiguation, asked of the terminal when the screen opens (`supports_keyboard_enhancement`, then `PushKeyboardEnhancementFlags`) and plain Enter elsewhere; Backspace with Option or Command takes a word or the line back the same way, as Ctrl-W and Ctrl-U do everywhere. `Draft::cursor` is a byte offset into the text: typing, a paste, a line break and a completion go in there, the deleting keys (`Cut`) take before it, and the arrows (`Move`) move it, by word with Option or Ctrl and to the line's ends with Command, which again only a terminal reporting them sends (Home, End, Ctrl-A, Ctrl-E and Terminal.app's Option-B and Option-F work everywhere); Up and Down stay with the completion list while it is open, and any move closes it until the next key typed, so passing through a mention never hands Enter to the list. The completion reads the word before the cursor and replaces the whole word, a space after it unless one is there. A correction, or its undoing, puts the cursor at the end. `ui::put_caret` draws the caret at the cursor, and the box scrolls so its row stays in view. Ctrl-G returns `Action::Fix` with the box's text when the config names a `fix_command` (`State::fixes`, which also puts the key in the box's hint, or holds what Ctrl-G says instead); the loop runs `fix::run` under a status line and hands the answer to `State::fixed`, which puts it in the box and keeps what was typed in `Draft::typed`, unless the answer is the text itself. Ctrl-G with `Draft::typed` set puts that back instead, and any change to the text clears it (`State::typed`), so the key never undoes an edit. Warnings raised while the screen is up are held by `warn.rs` and shown in the status line. The screen asks the terminal for focus reports (`EnableFocusChange`) and, when the terminal is one `notify::supported` names and you are known, hands each socket message to `App::notify` before `State::hear`: one `notify::aimed` takes, heard while the terminal does not have the focus, is written to stdout as `Note::sequence`, the conversation's label as title, the sender and the text with its markers dropped (`mrkdwn::strip`) as body, the names looked up on a miss. `App::keep_beat` follows the socket's `live` flag on each pass: the heartbeat is written every 30 seconds while it is up, and removed when it drops and when the screen quits, so the fallback takes over at once.
- `style.rs`: ANSI styling, off under `--no-color`, `NO_COLOR` or a non-terminal stdout. `par.rs`: a small ordered parallel map over a few threads for the lookups. `warn.rs`: warnings on the way to a result, on stderr, or held for the status line while the screen is up.

## Files on disk

| File                                     | Written by                                       | Read by                              | Deleting it                                    |
| ---------------------------------------- | ------------------------------------------------ | ------------------------------------ | ---------------------------------------------- |
| `~/.config/slack/workspaces.json` (0600) | `login`, `logout`                                | every command (`store.rs`)           | logs you out                                   |
| `~/.config/slack/browser-profile/`       | `login` (Chrome)                                 | `login --headless`                   | the next login needs the window again          |
| `~/.config/slack/config.toml`            | you, by hand                                     | the screen, on opening (`config.rs`) | Ctrl-G no longer corrects                      |
| `~/.cache/slack/names.json`              | every command that names something               | the same                             | safe, refilled on demand                       |
| `~/.cache/slack/last-view.json`          | the view, `show`, the screen and `read` (drops)  | `read`, `thread N`, `send N`         | safe; `read` and the numbers need a new output |
| `~/.cache/slack/notifying` (empty)       | the screen, while it notifies                    | `--count --json`                     | safe; a status bar may notify twice meanwhile  |
| `~/.cache/slack/files/<id>/` (0700)      | the screen's `u` on a file, dropped after 7 days | the screen, the system viewer        | safe, fetched again on demand                  |

`$XDG_CONFIG_HOME` and `$XDG_CACHE_HOME` move the two directories; `$SLACK_BROWSER_PROFILE` moves the profile alone.

## Contracts between modules

- **The unread rule lives in one place.** `Conversation::counts_as_unread` in `counts.rs` decides what the view lists and what `--count` counts; the view, the TUI and the count never re-decide.
- **One model for three outputs.** The text view, `--json` and the TUI items all come from `view::build`; only the `Reach` differs (the unread part for the first two, the recent history for the screen). A section or a field added to `View` shows up in all three.
- **What `read` may mark is what was shown.** `View::shown` lists the conversations whose messages were printed; `lastview` records them as listed. `slack show` records its conversation too, but not as listed, so a bare `slack read` leaves it alone and `slack read <name>` takes it. The TUI marks directly and drops the conversation from the record.
- **A number refers to the last output that printed one.** `View::thread_refs` numbers the threads in reading order; `show` replaces the numbering with its own; `last-view.json` keeps one numbering per workspace.
- **A missing name never fails a run.** `channel_label` and `user_label` fall back to the id, and `resolve_*`, which fetches per id on a miss, swallows a lookup that fails for one id. The directory walks (`walk_*`, when a directory is needed) do propagate their errors. The cache is written back at the end of the run.
- **Tokens stay below `api.rs`.** `Workspace` has no `Debug`, `api::Error` carries the method and Slack's error code but never the request, and nothing above the transport builds a header.
- **Only `https://*.slack.com` origins** are paired with the session cookie: `capture::is_slack_workspace_url` is the gate, and `is_slack_socket_url` its `wss://` twin for the socket `rtm.connect` names. `Client::download` goes through the same gate (files are served from `files.slack.com`) and follows no redirect.

## Error direction

An error must never look like "nothing to do", above all for `--count` in a status bar. Any Slack or transport failure fails the run with a non-zero exit. Undocumented endpoints (`client.counts`, `subscriptions.thread.getView`, `localConfig_v2`) are read defensively: a missing or changed shape is an `Error::Shape`, or a warning where degrading is the better call (the thread view, the history of one conversation, the preferences), never silence. Warnings go through `warn.rs`: stderr, or the status line while the screen is up.

## Tests

`cargo test` never talks to Slack. The pure modules (the parsers, the view model, `mrkdwn`, the TUI state, the capture extractors, the target syntax) are tested in-module, with `tests/fixtures/` for the response shapes. The transport, the CDP session, Slack's socket and the terminal loop are checked by hand: the read-only commands against a live session, and the TUI through a pseudo-terminal that sends keys and reads the screen.
