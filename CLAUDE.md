# CLAUDE.md

Guidance for Claude Code in this repository. `ARCHITECTURE.md` has the module map, the run of each command, the files on disk and the contracts between modules: read it before touching `src/`. This file is the workflow and the decisions.

## Commands

```bash
cargo build                                   # debug binary in target/debug/slack
cargo run -- --count                          # run a command
cargo test                                    # unit tests (pure modules, fixtures)
cargo clippy --all-targets -- -D warnings     # lint, warnings are errors
cargo fmt                                     # format
prettier --write "**/*.md"                    # Markdown
shellcheck tools/answer/answer tools/answer/test tools/answer/fixtures/gh && tools/answer/test   # the watch's command
```

## Workflow

Denis's personal project (`github.com/denrou/slack`, public, MIT). It runs the pull request flow of Denis's `personal-repos.md` rule (branches, squash merges, review, merge, release, ideas, backlog); only what this repository does differently is written here.

- **The docs that change with the code** include `skills/slack/SKILL.md`, the manual an agent reads before using the CLI: a command, an output or a rule it states.
- **Denis tries first** a change whose only proof is a live write (a send, a reaction, a mark as read, a status set), since only he runs those: `send --at` passed every test, and only a live run showed Slack refusing the token.
- **Release.** The version is `version` in `Cargo.toml` (`cargo build` so `Cargo.lock` follows), and the formula is `slack`. The tag push runs `.github/workflows/release.yml`: it checks the tag against the crate version and reads its notes (a tag without them fails there, before the builds), lints and tests, builds the macOS arm64 and Linux x86_64 binaries, publishes the GitHub Release with the tag's notes and the compare link, the archives (`slack-vX.Y.Z-<target>.tar.gz`) and `checksums.txt`, then asks `denrou/homebrew-tap` (shared with gh-prs and ggit) to rewrite the formula. `.github/workflows/ci.yml` runs fmt, clippy and the tests on every pull request and every push to `main`.
- **Live checks.** `slack login` needs a human in the Chrome window; once the session is saved, every read-only command (`whoami`, `--count`, `unreads`, a bare `status`) can be run from here to check the output. **Never run `send`, `react`, `read`, or `status` with anything to set or clear, from here**, not even to see an error path: `read` acts on whatever `~/.cache/slack/last-view.json` holds, and on 2026-10-19 a run meant to show the "nothing to mark" message marked eight channels as read instead. Inspect the cache file; leave the writes to the user. `slack watch` sends nothing and can be run from here, with `XDG_STATE_HOME` in the scratchpad so Denis's own log stays his. So can `tools/answer/answer` on its fixtures, with `ANSWER_GH=tools/answer/fixtures/gh` and `XDG_STATE_HOME` and `XDG_CONFIG_HOME` in the scratchpad: it never reaches Slack, and each event costs three Sonnet calls on Denis's subscription.

## Security rules

- Never print, log or serialise a token (`xoxc`, `xoxd`, the Cookie header), in output, errors or `--json`.
- Only `https://*.slack.com` origins, never `app.slack.com`, may be paired with the session cookie: `capture::is_slack_workspace_url` is the gate, and it is load-bearing.
- A profile path from the environment is user input: a directory without our sentinel is never reused and never deleted.

## Decisions (2026-10-19)

Written down because none of them can be read from the code.

- **Blocking I/O, no async runtime.** A handful of sequential HTTP calls, one WebSocket for the capture, a `std::thread::scope` for the lookups. Switching later would cost `api.rs` and `auth/cdp.rs`, not the pure modules.
- **Credentials in `workspaces.json` (mode 0600), not the Keychain.** The footer polls `slack --count --json` from a launchd job (`~/.local/bin/update-dev-status`, its SLACK and @ME cells read `unread` and `me`), and the Keychain prompts whenever the binary changes, which is every rebuild. The browser profile next to it is a plaintext credential store anyway. A keychain backend can come later as an opt-in.
- **Mark-as-read is explicit** (`slack read`), never a side effect of reading, so the footer count keeps agreeing with the Slack app. A mark never moves a cursor back: what the app read since is left alone.
- **Slack's own mute list is honoured; there is no local one.**
- **Every unread conversation is shown, muted ones excepted (2026-10-20).** The first rule hid public channels unless private or set to "All new messages" in Slack, and twice hid a channel Denis wanted to see (`#log-team-dev`, then `#proj-prediction-service`). He mutes what he does not want, so the rest is wanted: the view and the count follow Slack's sidebar. The `-a` tier (`slack -a`, `--count --all`, `ui -a`, `read --all`, the `a` key) went with it.
- **Search is Slack's own (2026-10-21).** `slack search` sends the query to `search.messages` as typed, so Slack's operators work and nothing is indexed here; the newest matches first, not Slack's relevance, since what is looked for from a terminal is usually recent. One page, 20 by default and 100 at most: Slack's operators narrow rather than a second page.
- **Who is around, for the people in view (2026-10-23).** What Denis wants is whether he can write to someone now, which status and the other person's clock answer better than the dot. So `slack who` takes named people, a channel's members (50 at most) or the recent DMs, never the whole workspace: Slack has no bulk presence call any more (one `users.getPresence` each, hundreds at Centreon) and keeps no history, so "who was online at 10:00" cannot be answered at all. Left out on purpose: group DMs, and someone else's snooze, which `dnd.teamInfo` does not give.
- **No interactive screen (2026-10-28).** `slack` alone opened a ratatui screen since 2026-10-19 (list and messages panes, replies, reactions, the picker, Slack's socket, notifications, images, the Ctrl-G correction): about 11,000 lines with its socket, notifier and file viewer. In use Denis rarely opened it: the correction he valued moved to a Hammerspoon key that works in the Slack app itself, and the use that stuck is Claude Code through the skill, which only needs the commands. So the screen went, and `slack` alone prints `slack unreads`. A terminal client is slk's job if one is ever wanted; bringing the screen back would be `git show v0.18.1:src/tui/`, not a port.
- **Watch, a dry run first (2026-10-28).** Denis works six hours behind most of his colleagues, so a question asked during his night waits for his morning. `slack watch` hands each DM and each mention of him (`<@him>`, never `@here`, `@channel` or a group) to a command of his, which reads the exchange on stdin and prints a reply. The command is `tools/answer/` (see its own decision). Three things are deliberate. The command never gets Slack, only text, and the CLI alone decides where a reply would go. The marker `🤖 Réponse automatique :` is added by the CLI, so no prompt can drop it. And nothing is sent yet: the watch runs all day and logs what it would send next to what Denis wrote afterwards, so the prompts are tuned on real exchanges before security and IT look at it. Sending, when it comes, is a decision of its own, with a window (his nights, his days off, which France does not share) and a limit per conversation so two auto-responders cannot answer each other. Slack's socket came back for it (`rtm.rs`, from v0.18.1): it hears a message whether or not it was read since, and a mention in any thread, which polling `client.counts` cannot.
- **The answer command: a reply only when it does something (2026-10-28).** `tools/answer/answer` is what Denis runs under the watch. A reply that only says he is away is no use to anyone, so one goes out in three cases only: a review asked on a pull request that has not had the automated review (`/check-pr`, its comment or the `ai-reviewed` label), where the reply says he will review it and asks for that first; something urgent (production down, a customer blocked), where it says when Slack will notify him; and someone playing with the bot, once, with a joke. Anything else waits for him, a review already through the automated one included, since then it is his to read. Three `claude -p` calls on Sonnet 5.5, on Denis's subscription rather than an API key: a judge, a responder, a reviewer that only passes or rejects, since a rewrite would go out unchecked. The models get no tools: what a reply rests on is read by code and handed over as facts, the pull requests through `gh` (a colleague's links only, never for someone from another organisation) and the time from the event (`notifications_paused_until`, or a status's end when later, and no time at all while notifications are not paused, since Slack notifies him then), so a message cannot steer a lookup. The calendar was the first idea for the time; the claude.ai connector is out of reach under the flags below (2026-10-28), and Slack's pause is the moment he is notified anyway. The rules that must not rest on a model are code too: the skip list, another auto-reply, one reply per conversation in 12 hours, one playful reply per sender in 7 days, and a draft with an `@`, a link or a phone number. Everything fails closed: a failed call exits non-zero, which the watch logs, and prints nothing. The script's clock is the last trigger's `ts`, so the same event always reads the same. The script and the prompts are in the repository, written about "the owner" so nothing in them is Denis's; what is his (`private.md`, the list the reviewer checks against, and `skip`) is in `~/.config/slack/answer/`, since the repository is public and that list would publish what it protects. The calls run in an empty folder with `--tools "" --strict-mcp-config --setting-sources ""`, which on 2026-10-28 kept every `CLAUDE.md`, rule, memory, connector and tool away from the model; the account email still comes through, and the `@` check is what stops it. `--bare` would remove it too but takes only an API key.
- **A status that Slack ends (2026-10-29).** Denis wants his status to follow his day: off for the night from 17:00 to 07:30, in a meeting during one. `slack status` sets, clears or shows his own status, and its end is Slack's `status_expiration` (`--until`), not a second job that clears it: launchd runs a job missed while the Mac sleeps at the next wake, several merged into one, so a 17:00 set and a 07:30 clear both missed overnight would fire together in the morning in no set order, while Slack clears an expiry on its side with the Mac off. `--if-unset` leaves a status already set alone, so the evening job never replaces a days-off status set by hand. The calendar sets it from outside the repository: Slack's Google Calendar app would do it, but Centreon's free plan keeps a short list of apps that leaves it out, and the claude.ai connector is the one calendar access already signed in. `claude -p` reaches it when the calendar tool is allowed and `--tools` is left alone (2026-10-29), so Denis's own schedule (`~/.local/bin/update-slack-status`, a launchd tick each minute) asks Haiku for the events, decides in code, and calls `slack status`; `slack status --json` tells it a status of its own from one set by hand. It keeps one value on disk, when to act next (the next meeting's start, 07:30 or 17:00), so Claude is asked a few times a day, not on every tick. It lives outside the repository because it is his schedule, its texts and its hours.
- **A message Slack posts later (2026-11-04).** Denis works six hours behind most of his colleagues, so an answer written in his afternoon lands in their evening. `slack send --at` has Slack post it, with the Mac asleep, as for a status's end; the times are `--until`'s (`when.rs`). `chat.scheduleMessage` refuses a session token (`not_allowed_token_type`, as slackcli found too), so the message goes the way the Slack app schedules one, captured from the browser on 2026-11-04: `drafts.create` with `date_scheduled` and the text as rich text `blocks` (`mrkdwn::rich_text`), undocumented like `client.counts`. Left out on purpose: listing and cancelling, which the Slack app does where the message would be looked for. `send --draft` is the same call without the time: the message waits in the Slack app's drafts, in its conversation and thread, on every device.
- **Claude drafts, Denis sends (2026-11-05).** A message from Denis is one people expect him to write, so by default he presses send himself, in the Slack app: the skill writes the draft in the conversation and, once he is happy with it, leaves it in that conversation's Slack drafts (`send --draft`). It posts a message itself in two cases only: a scheduled one (`send --at`), which he can still review, edit or cancel in Slack's scheduled messages before it goes out, and one he reread and asked to be sent as is (plain `send`, since the same day: opening Slack only to press send on a message he has nothing to change in is a round trip). What keeps the reason intact there is exactness: the text he reread, to the target shown with it, through a quoted heredoc so the shell changes nothing, nothing changed after his ask, one ask for one message, and a draft whenever the wording leaves it open. A guard in the CLI was left out (#72): the model would pass the flag itself, so it would prove nothing the rule does not. The draft pane went with it: `tools/draft-pane/` (2026-10-29), a Claude Code mod that opened the draft beside the chat with Send, Schedule, Fix, Chat and Copy. Its Send posted at a click, with no ask in words, editing moved to the Slack app with the draft, and the spelling fix it carried is the Hammerspoon key there. Bringing it back would be `git show v0.21.0:tools/draft-pane/`. Plain `slack send` stays in the CLI for a person at a terminal; the rule is the skill's.
- **Binary name `slack`**, kept because it is fast to type. Slack's platform CLI (`brew install slack-cli`) also installs a `slack` binary; it is not on this machine.
- **Public repo, MIT**, like gh-prs.

Kept from slackcli: the browser-session credentials and their capture (`auth/`). Deliberately not ported: app tokens, `parse-curl`, drafts and scheduling (built natively later, as `send --draft` and `send --at`), canvases, the custom emoji list, file uploads and listings, saved items, user groups, the update checker, log files, Windows. If one becomes needed, it is a feature, not a port.

## Reference implementation

[slackcli](https://github.com/shaharia-lab/slackcli) (TypeScript, Bun) is installed on this machine as `slackcli` and logged in. Clone it into a scratch directory to compare how an endpoint is handled; `src/lib/browser-auth.ts`, `browser-launcher.ts`, `cdp-client.ts`, `unread.ts` and `unread-messages.ts` are the files these modules were ported from. Its `docs/user-guide/authentication.md` documents the two credential kinds.

## Testing

Pure modules are unit-tested in-module. Most response shapes are inline `json!` in the modules' tests; `tests/fixtures/` holds the larger ones, with ids and names made up: `client_counts.json` was written from slackcli's field list and checked field for field against a live response on 2026-10-19 (the live one also carries `updated`, `history_invalid`, `channel_badges`, `activity_v2`, `alerts`, `saved`, none of which is read).
